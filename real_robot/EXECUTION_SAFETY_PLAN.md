# xArm7 execution preparation and safety review

Historical single-action executor notes. The current batched loop is documented in [RUN_PIPELINE.md](RUN_PIPELINE.md). Two physical Knock attempts did not establish validated contact behavior; a successful xArm command is not proof of box clearance.

Original status: **code and disconnected stage generation only**. The robot at `192.168.1.231` has not been connected to or moved by this executor. The user asked to be told before every real execution; do not invoke `--execute` until the user has reviewed a completed configuration and the generated one-action stage JSON, and approved that specific physical action.

The real executor is [`xarm_executor.py`](xarm_executor.py). It consumes the verified `layout_and_plan.json` from the existing solver, not a separate action planner. `--step` selects exactly one high-level action. Each action is built in `link_base`; the SDK receives Cartesian positions in mm and roll/pitch/yaw in degrees. The default path is disconnected. The SDK import, robot connection, TCP setting, enabling, and motion calls exist only in the `--execute` branch. The [configuration template](execution_config.example.json) intentionally contains `null` for unmeasured safety-critical values and has review flags set to `false`.

## Action phases

- **Pick:** pre-pick at transit height; open fingers; descend to approach then pick height; close slowly to an aperture selected from the box closing side; lift vertically; raise to transit height; travel laterally above the bowl; descend to the measured release height; open; retreat vertically. The plan's `pick-x` or `pick-y` witness determines the closing side and tangential contact position.
- **Knock/Clearance:** close the gripper empty; pre-knock at transit height; descend above the target; approach the measured top face; make one shallow, slow, outward stroke of at most 15 mm; release vertically; retreat. This mirrors the Isaac top-edge outward contact primitive, but deliberately stops for a new RGB-D observation. The Isaac contact bias is **not transferred** to the xArm: the xArm needs its own TCP and pad-to-contact calibration. No blind retry or automatic PickPlace is allowed after a Knock.

The current 2 × 2 run's abstract plan is Knock 3, Knock 4, Pick 1, Pick 2. A Knock's mandatory PickPlace is only safe after measuring the displaced box's new pose. Capture a fresh frame, run SAM 2 / FoundationPose / solver, inspect the result, then generate a new single-action preview. Do not continue with the old scene's remaining steps after any physical change without that review.

Two user-approved empty-gripper calibration commands from about 842 toward 570 pulses returned SDK code 0 but caused no visible movement or meaningful pulse change. The first used speed setting 10 and SDK auto-enable; the second set gripper mode 0, enabled the gripper, set speed 100, then sent the command. The user confirmed nothing obstructed the fingers. The user-provided working `test_xarm.py` also enables arm motion, sets mode 0 and state 0, and selects gripper speed 3000 before gripper commands. ## Gentle-grip rule

The object class determines the commanded *aperture*, not a raw motor pulse. For the current Protex Pick across a 58 mm effective planning side, the template's `gentle_compression_mm = 1` gives a 57 mm target. The executor converts that aperture to a pulse using two **measured** aperture/pulse pairs. Example only: if 0 pulses were measured at 0 mm and 850 pulses at 85 mm, 57 mm would map to 570 pulses. Those values are synthetic test data and must not be entered as calibration without measuring the physical gripper. The standard gripper's position command and low speed do not impose a contact-force limit; a compressible package still requires a supervised force/damage trial before automatic closure. The SDK gripper speed is a device setting, not a validated physical closing speed; the working lab script uses 3000. The executor accepts settings 1–3000, but contact with compressible packaging still requires supervised calibration. The gripper's approximate 85 mm opening does not support an 88 mm long-side grasp plus margin.

## Bowl routing

The revised **selected drop points** are `(600, -100)` and `(600, 100)` mm in `link_base`; the user will place bowls at these points before a release. their given `z=0` denotes the table plane, not a safe release height. The example template still leaves each bowl's `release_z_mm` and `inner_radius_mm` unset. A separate provisional preview config assumes 90 mm and 90 mm solely to generate waypoints; the values are not verified and `provisional=true` blocks execution. These must be measured, along with bowl rim height and a release position that keeps the box inside the bowl without a damaging drop. The fallback assignment alternates bowls deterministically across planned Picks; `instance_to_bowl` can override it after human label inspection. Neither SAM 2 nor FoundationPose identifies Protex “Skin Purifying” versus “Fresh,” so no subtype-based routing is claimed. Beach Rd variants likewise need a separate appearance/OCR check or manual mapping.

A [read-only controller readback](experiments/protex_4_20260914_183700/execution_preparation/controller_readback.json) found a configured TCP offset of `[0, 0, 172, 0, 0, 0]` mm/degrees, current TCP pose around `(540, 17, 563)` mm, gripper at 842 pulses, and no controller error. These are live settings, not validated contact calibration. The example configuration remains blocked.

After the exploratory IK calls, a subsequent read-only controller check reported warning code 14 with error code 0 and unchanged TCP pose. The executor now blocks on any warning as well as any error. The SDK defines warning 14 as “command has no solution.” Because our rejected read-only IK probes caused it, the warning alone was cleared with `clean_warn()`; a subsequent readback showed `[error, warning] = [0, 0]`, state 2, and the same TCP pose. No error reset, motor enable, or motion was performed.

A [read-only IK screen](experiments/protex_4_20260914_183700/execution_preparation/hypothetical_ik_screen.json) used hypothetical top-down roll/pitch `(180°, 0°)`, TCP contact offset 0 mm, release height 90 mm, and transit height 300 mm. It returned feasible IK for source Pick/Knock waypoints, but SDK code 10 for both bowl transfer/retreat waypoints at the user-provisional `(700, ±100)` mm bowl centres. At the same top-down orientation and 300 mm height, exploratory read-only IK returned success around `(600–625, ±100)` mm; a +30° wrist pitch also returned IK at 700 mm, but a tilted carried-box path has not been validated. Therefore neither a bowl relocation nor wrist tilt should be assumed silently. The executor's per-stage IK preflight will reject the current top-down bowl transfer before motor enabling. IK success checks reachability only, not collision or acceptable grip loading.

A later read-only audit found controller collision sensitivity `0` (off), TCP payload `0 kg`, and state `4` (stopped), with no error or warning. The executor now rejects motion if sensitivity is below 3, gripper payload is absent, or state is stopped. [UFACTORY Studio settings](https://docs.ufactory.cc/user_manual/ufactoryStudio/7.settings.html) list the standard xArm gripper TCP offset as 172 mm and nominal TCP payload as 0.82 kg with centre of gravity 48 mm on Z; the observed 172 mm offset is consistent with that default, but the payload is not configured. These controller values and the stop state must be deliberately restored and checked under the lab safety procedure before any physical action. No settings were changed during this audit.

## Measurements and checks before motion

1. Verify `T_link_base_camera_color_optical_frame` against several known points on the table and verify `table_z_mm`. The current transform was supplied and applied, but not physically checked.
2. Measure the xArm controller TCP offset, top-down roll/pitch and yaw-to-closing-axis relation, and the offset from commanded TCP to the gripper pad/contact surface. Fill `tcp_offset_mm_deg`, `tool_roll_pitch_deg`, `tool_closing_axis_yaw_offset_deg`, and `tcp_contact_z_offset_mm`. The height clarification is 28 mm nominal soap-box height, but it also needs measurement for contact. This is separate from the FoundationPose mesh currently still using 30 mm.
3. Measure gripper aperture at two known SDK pulse positions, including an opening near the 55–60 mm working region, then fill `gripper_aperture_calibration`. Verify the desired 57 mm target on a box with a scale or force gauge at low speed; adjust gentle compression downward if packaging deforms. The standard gripper SDK reports pulses, not mm.
4. Measure both bowls' inner radii, rim and safe release heights. Fill a conservative 3-D workspace and transit, lift, and approach heights. Validate every resulting stage, intervening segment, and tool envelope for self-collision, table, bowls, fixtures, the camera, and bystanders. Current code checks waypoint bounds and uses vertical staging; it is **not** a full robot collision planner.
5. Validate a single short Knock contact on a sacrificial box with an observer and emergency stop accessible. Confirm the displaced box's measured travel and no damage before considering longer or repeated contacts. With no force/torque feedback integrated, speed limits alone do not guarantee gentle contact.
6. Review and approve one concrete stage JSON. The executor requires `contact_execution_reviewed=true` and matching `approved_plan_id` before motion, plus `knock_contact_validated=true` for a Knock. Later steps require a fresh scene review flag. These software gates supplement, but do not replace, the human safety review.
